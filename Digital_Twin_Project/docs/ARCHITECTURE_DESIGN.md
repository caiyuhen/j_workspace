# 架构设计文档

## 1. 架构风格
本项目采用 **微服务架构 (Microservices Architecture)**。每个核心业务功能被封装为一个独立部署的服务，服务之间通过轻量级 HTTP (REST API) 进行通信。

## 2. 服务组件

### 2.1 报告网关 (Report Gateway)
*   **角色**: API 网关 / 编排器 (Orchestrator)
*   **技术**: Python, FastAPI, HTTPX
*   **职责**:
    *   统一入口：客户端只与网关交互。
    *   请求路由：将请求转发到后端服务。
    *   业务编排：协调 OCR -> 患者 -> 模拟 -> 可视化 的调用链。

### 2.2 OCR 服务 (OCR Service)
*   **角色**: 基础设施服务 / 数据提取
*   **技术**: Python, RapidOCR / PaddleOCR, PDFPlumber
*   **职责**:
    *   处理非结构化数据（PDF/图像）。
    *   提供 OCR 能力作为通用服务。
    *   实现与特定业务逻辑解耦的文本提取。

### 2.3 患者服务 (Patient Service)
*   **角色**: 领域服务 (Domain Service)
*   **技术**: Python, FastAPI
*   **端口**: 8003
*   **职责**:
    *   作为患者数据的“事实来源”。
    *   解析 OCR 原始文本为领域模型（如解析 Cobb 角）。
    *   管理患者档案数据。

### 2.4 模拟服务 (Simulation Service)
*   **角色**: 计算服务 / 核心业务逻辑
*   **技术**: Python, NumPy, SciPy (未来可能集成 FEM 求解器)
*   **端口**: 8001
*   **职责**:
    *   执行计算密集型任务。
    *   实现脊柱生长和生物力学算法。
    *   支持按“周”进行时间步进的演变模拟。
    *   无状态设计，便于横向扩展。

### 2.5 可视化服务 (Visualization Service)
*   **角色**: 渲染服务 / 表现层支持
*   **技术**: Python, Plotly, VTK (未来)
*   **端口**: 8002
*   **职责**:
    *   将数值数据转换为图形表示。
    *   生成图表配置 (JSON) 或 3D 模型文件 (GLB/OBJ)。
    *   生成带有时间滑块和动画帧的交互式图表。

## 3. 数据流设计

### 场景：生成演变报告

1.  **用户** 上传 PDF 到 **网关**。
2.  **网关** 将 PDF 流式传输到 **OCR 服务**。
3.  **OCR 服务** 返回提取的文本和 JSON 数据。
4.  **网关** 将 OCR 数据保存到共享存储（或数据库），并通知 **患者服务**。
5.  **用户** 请求生成报告（带有治疗参数）。
6.  **网关** 从 **患者服务** 获取当前脊柱状态。
7.  **网关** 调用 **模拟服务**，输入当前状态和治疗参数。
8.  **模拟服务** 返回未来数周/数月的脊柱状态序列。
9.  **网关** 将模拟结果发送给 **可视化服务**。
10. **可视化服务** 返回带有时间滑块配置的 Plotly JSON。
11. **网关** 组装最终 JSON 响应返回给 **用户**。

## 4. 部署架构

*   **容器化**: 每个服务打包为一个 Docker 容器。
*   **编排**: 使用 Docker Compose 进行本地开发和测试编排。
*   **网络**: 服务运行在同一个 Docker 网络中，通过服务名称（如 `http://patient-service:8000`）相互发现。

## 5. 扩展性考虑

*   **独立扩展**: 模拟服务如果是计算瓶颈，可以单独部署多个实例并负载均衡。
*   **技术异构**: OCR 服务可以使用 GPU 优化的镜像，而网关可以使用轻量级镜像。
*   **故障隔离**: 如果可视化服务崩溃，网关仍可返回原始数据，不影响核心业务数据。
