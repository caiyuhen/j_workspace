#  医疗数据清洗与治理平台功能说明文档

## 一、系统概述
本平台是一个端到端的医疗数据治理系统，旨在将非结构化的医院原始数据（如 CSV 电子病历、DICOM 影像文件）经过自动化解析、NLP 实体提取和深度清洗，最终归一化并落盘到符合国际数据标准的数据库中。系统采用前后端分离架构，提供可视化的数据接入工作台与清洗质量评估大屏。（只符合80%的数据清洗标准，20%的个性化数据清洗标准实现，链接真实数据需要在再做调整）

## 二、核心功能模块与特性

### 1. 数据接入工作台 (Data Ingestion Workspace)
该模块是用户与系统交互的第一站，负责所有原始数据的接入、解析与状态追踪。

*   **多文件高并发上传**
    *   支持一次性选择并上传多个 CSV 结构化文件或 DICOM 影像文件。
    *   异步处理机制：上传后立刻返回状态，后台队列负责逐个解析，不阻塞前端操作。
*   **DICOM 影像数据的“双轨制”清洗与归档**
    *   **物理层安全隔离 (MinIO 集成)**：由于 DICOM 属于大体积非结构化二进制数据，系统上传接口（`/api/v1/dicom`）会利用 SDK 直接将影像文件流式写入本地 MinIO 对象存储的 `dicom-images` 存储桶中，实现与关系型数据库的物理隔离。并在数据库中仅保留该文件的安全存储路径（如 `s3://dicom-images/uuid.dcm`）。
    *   **头部元数据结构化提取 (Metadata Extraction)**：内置 `pydicom` 引擎负责“拆解” DICOM 的 Header 标签。精准提取如 `PatientID`（患者唯一标识）、`PatientBirthDate`（自动转为年龄）、`Modality`（检查模态，如 CT/MR）以及 `BodyPartExamined`（检查部位）等高价值医疗元数据，将其转化为标准 `StagingObservation` 记录并存入 SQLite 暂存区。
    *   **孤立影像拯救机制 (Dummy Patient)**：清洗管线内置智能巡检。若发现单纯的影像记录缺乏对应的人口学主档信息（即“孤立数据”），引擎会在内存中为其动态生成虚拟患者档案（Dummy Patient），确保影像在最终数据归一化时不会被遗漏丢弃。
    *   **前端在线追踪与预览**：前端探查大屏支持通过 MinIO 预签名 URL，一键下载或在线预览经过脱敏处理的 DICOM 原片。
*   **全景数据分布探查 (Data Profiling)**
    *   独立的全屏沉浸式探查页面。
    *   对上传的 CSV 批次数据进行自动画像，利用 Pandas 计算每个字段的数据类型、空值率以及 Top 10 值分布，辅助用户在清洗前了解数据质量。
*   **一键数据清空**
    *   提供全局数据复位能力，支持一键清空 SQLite 暂存区、本地缓存文件，并递归删除 MinIO 存储桶中的影像数据。

### 2. NLP 深度语义提取引擎 (NLP Extraction Engine)
在数据从原始区进入暂存区时，平台会拦截如“主诉”、“现病史”、“影像报告”、“出院小结”等非结构化纯文本字段，通过双核引擎（深度学习模型 + 增强正则）进行全自动的实体抽提。

*   **双核提取架构与逻辑**
    *   **医疗垂直深度大模型 (NER)**：底层引擎已升级为 `shibing624/macbert4ner-base-chinese`。这是一个基于顶级中文开源模型 MacBERT，并在 CMeEE（中文医学命名实体识别）数据集上深度微调的专业医疗模型。相比通用模型，它天生精通医学黑话，能够极其精准地将文本分类为 `DIS` (疾病)、`SYM` (临床表现)、`DRU` (药物)、`PRO` (医疗程序) 及 `BOD` (身体部位)。
    *   **高精度正则规则过滤引擎**：模型在处理结构化数字时容易产生碎片化数据。为此，系统在送入模型之前，部署了的前置正则引擎：
        *   **阴性/否定防幻觉系统 (Negation Detection)**：精准拦截 `(否认|无|未发现|未见) + (疾病/症状)` 的句式。例如将“否认高血压史”直接拦截并转化为阴性诊断 `排除/阴性：高血压 (否认)`，并将其从原文本中“挖除”，彻底阻断大模型将其误认为既有疾病的可能。
        *   **生化指标穿透提取**：兼容中英互通的指标提取能力。无论是标准格式的 `检查项：空腹血糖 值:6.5`，还是混合英文的 `WBC 7.2`，亦或是 `Glucose 5.4`，都能被正则引擎精确捕获并剥离，防止被大模型拆散为无意义的数字碎片。

*   **核心数据提取**
    1.  **疾病与症状 (Conditions/Symptoms)**
        *   从长文本中识别患者的疾病状态。提取出的疾病与症状将自动落入的 `conditions`（诊断）。
    2.  **药品与处方 (Medications/Drugs)**
        *   识别文本中的治疗用药（如 `左氧氟沙星`），并自动落入 `medications`（用药记录表）。
    3.  **生化体征与检验 (Measurements)**
        *   拦截并剥离混合文本中的医疗指标、数值和单位。提取结果将被标准化为 `检查项：{名称} 值:{数值} 单位:{单位}` 的统一格式（如 `检查项：空腹血糖 值:6.5`），并存入 `measurements` 表。
    4.  **带数值的症状 (Symptoms with Values)**
        *   识别本质上属于生命体征的症状描述。例如将 `"症状：发热 值:38.5 单位:度"` 剥离，作为体征存入 `measurements` 表中。
    5.  **绝对与相对时间 (Times) & 阴性排查**
        *   精准捕获 `3天前`、`2个月后` 等时序描述。连同被前置正则拦截下来的“阴性诊断”（如 `排除/阴性：骨折 (未见)`），一起存为 `observations`（临床观察表），方便前端溯源病程时间线。

*   **GPU 硬件加速与批处理性能 (Performance & Batch Processing)**
    *   **智能硬件嗅探**：系统初始化时自动检测宿主机环境，若存在 NVIDIA 显卡及 CUDA 环境，模型张量将自动加载至 GPU 显存中，否则平滑降级至 CPU 运行。
    *   **一波流批处理 (Batch Inference)**：改变了传统的“单条记录循环调用”模式，而是将单个批次（Chunk）内成百上千条的文本（如10,000条记录）统一收集入 `nlp_tasks` 任务池，随后以 `Batch=16` 的规模一次性送入模型推理。这极大地减少了 I/O 损耗，在 GPU 环境下可实现数十倍的性能飞跃。

### 3. 数据清洗与归一化管线 (Pipeline)
这是系统的核心处理中枢，负责将 SQLite 暂存区中散落的实体数据进行严格的清洗、对齐，并重组为结构化的归一化格式。

*   **数据聚合与患者主轴重组 (Patient-Centric Aggregation)**
    *   **散列数据融合**：将在 NLP 阶段被拆散到不同表中的诊断、用药、体征、病程记录，以 `PatientID` 为主键进行重新关联。
    *   **时序化组装**：将同一名患者在不同时间点发生的医疗行为按照时间轴串联，形成一个完整的、深层嵌套的患者就诊全景 JSON。
*   **标准概念对齐与归一化 (Standard Concept Mapping)**
    *   **医学术语字典映射**：内置连接 PostgreSQL 术语标准库的能力，利用本地维护的 ICD-10 等医学词典，尝试将提取出的各种口语化、不规范的本地疾病词或检查项目（如“糖高”、“WBC”）映射为全球通用的 Standard Concept ID。
    *   **统一单位度量**：对生化指标的数值和单位进行规范化校验，将杂乱的单位（如“度”、“℃”）归一化为标准的国际单位制，确保后续数据分析的口径一致。
*   **孤立数据巡检 (Data Imputation)**
    *   具备智能数据兜底逻辑。对于仅有影像检查（DICOM）但缺乏人口学主记录的“孤立数据”，管线会自动为其动态检索患者档案 (Dummy Patient)进行匹配，确保医学影像数据不会在流转中丢失。（根据影像时间、检查开发出时间、影像文件名进行匹配）
*   **跨库异构写入 (Heterogeneous Data Sync)**
    *   经过严格清洗、对齐和结构化重组后的患者全量病历（包含诊断、化验、处方等明细的嵌套 JSON 格式），最终安全写入生产环境的 MongoDB (`192.168.0.214`) 集群。

### 4. 数据质量评估与可视化 (Quality Assessment Dashboard)
当管线执行完毕后，前端提供丰富的可视化图表用于评估清洗效果。

*   **实时数据分布**
    *   通过 MongoDB 的聚合查询 (Aggregation Pipeline)，实时展示成功落盘的诊断、生化检验、处方药品的总数和标准化对齐率。
*   **NLP 深度语义提取分析 (NLP Stats)**
    *   针对长文本中提取出的内容提供单独的分析面板。直观展示“疾病与症状 (Top 10)”、“提取药品 (Top 10)”以及“独立文本观察”的频次分布（通过微型比例条展示）。
*   **清洗前后对比视图 (Data Comparison)**
    *   随机抽取单名患者或指定患者，并排展示其原始 CSV/DICOM 数据与最终落入 MongoDB 的深层嵌套 JSON 标准化数据，帮助数据工程师直观验证映射逻辑的正确性。
*   **优雅降级与网络容错**
    *   在开发或沙盒环境中，如果目标 MongoDB 网络不可达，系统会优雅降级并展示友好的错误提示，而不是直接崩溃。

## 三、系统流转时序简述
1. 用户上传文件 -> **FastAPI** 异步接收 -> 写入 SQLite (`RawRecord`)
2. 触发 **StagingTransformer** -> 执行清洗空值、性别映射、时间转换
3. 拦截长文本 -> 触发 **NLP 批处理推理** -> 提取疾病/指标/时间 -> 写入 SQLite 暂存表 (`StagingXxx`)
4. 用户点击执行管线 -> 触发 **Pipeline** -> 组装患者主轴、映射标准术语
5. 最终落盘 -> 写入 **MongoDB** 目标库 -> 前端实时渲染。
