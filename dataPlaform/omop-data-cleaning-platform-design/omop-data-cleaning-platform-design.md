# 符合 OMOP 的医疗数据清洗平台产品设计

## 文档说明

本文档根据“医院数据来源可能是 API 或 CSV 导出，平台需要支持数据回溯、归一化、结构化、自动映射到 OMOP 表、数据验证、质量评估、数据治理并最终入库”的需求重新撰写。它不是从 HTML 页面直接转换而来，而是按 Markdown 技术产品文档的阅读方式重新组织。

目标读者包括产品负责人、数据平台研发、数据工程师、医学术语专家、数据治理团队和真实世界研究团队。

## 1. 产品定位

该平台定位为医院源数据进入 OMOP CDM 数据库前的清洗、映射、验证、治理与发布系统。它不只是 ETL 工具，也不是简单的数据上传系统，而是围绕 OMOP 标准建立的一套医疗数据生产平台。

OMOP CDM 的价值在于把来源不同、结构不同、编码不同的观察性医疗数据转换为统一的数据模型和统一的术语表达。平台需要解决三类核心问题：

1. 医院源系统差异导致的数据结构不一致。
2. 本地诊断、药品、检验、手术等编码与 OMOP 标准概念之间的语义差异。
3. 医疗研究使用数据前必须满足的数据质量、审计和回溯要求。

## 2. 建设目标

平台应达到以下目标：

| 目标 | 说明 |
|---|---|
| 多源接入 | 支持医院 API、CSV 文件、SFTP 文件、数据库视图等来源。 |
| 原始数据留痕 | 每次接入都保存原始数据快照、批次号、文件哈希、记录数和接入时间。 |
| 数据归一化 | 统一日期、数值、单位、枚举、空值、编码、字段类型和患者标识。 |
| OMOP 自动映射 | 自动推荐源表到 OMOP 表、源字段到 OMOP 字段、源编码到标准 concept_id 的映射。 |
| 人工审核 | 对诊断、药品、检验、手术等高风险映射提供医学专家审核流程。 |
| 数据验证 | 在入库前执行结构、必填、值域、外键、概念域、时间逻辑等校验。 |
| 质量评估 | 生成表级、字段级、概念级和批次级质量报告，可接入 OHDSI DataQualityDashboard。 |
| 数据回溯 | 从 OMOP 目标记录反查源记录、处理规则、映射版本、任务批次和发布版本。 |
| 数据治理 | 管理数据目录、敏感字段、权限、审批、发布、审计日志和数据生命周期。 |
| OMOP 入库 | 将通过校验的数据发布到 OMOP CDM 数据库，并形成可复用的数据版本。 |

## 3. 核心用户

| 用户角色 | 关注点 | 典型任务 |
|---|---|---|
| 数据工程师 | 接入稳定性、转换效率、失败定位 | 配置数据源、运行清洗任务、修复失败批次。 |
| 医学信息专家 | 医学语义是否准确 | 审核 ICD、药品、检验、手术、本地字典到 OMOP 标准概念的映射。 |
| 研究人员 | 数据能否用于研究 | 查看 OMOP 数据覆盖范围、质量报告、字段缺失和概念分布。 |
| 数据治理团队 | 权限、审计、敏感数据和发布流程 | 管理数据目录、字段分级、访问权限和发布审批。 |
| 平台管理员 | 多医院、多项目、多环境运维 | 管理租户、环境、连接、任务监控和系统配置。 |

## 4. 总体数据流程

平台的数据流程建议设计为以下链路：

```text
医院数据源
  → 数据接入
  → 原始数据区 Raw Zone
  → 数据剖析
  → 数据清洗与标准化
  → OMOP 字段映射
  → OMOP 概念映射
  → Staging 转换区
  → 数据验证与质量评估
  → OMOP CDM 发布库
  → 数据版本、质量报告与血缘回溯
```

每个阶段都要生成元数据。元数据包括源批次、字段画像、清洗规则版本、映射版本、任务运行记录、质量检查结果和发布版本。

## 5. 产品架构

### 5.1 架构分层

平台建议采用前端工作台、后端业务服务、任务编排、数据计算、数据存储和安全治理六层架构。

| 层级 | 组成 | 主要职责 |
|---|---|---|
| 前端工作台 | 数据接入、字段剖析、清洗规则、OMOP 映射、质量看板、血缘回溯、治理中心 | 为数据工程师、医学专家和治理人员提供可视化操作入口。 |
| 后端业务服务 | 认证授权、项目服务、数据源服务、元数据服务、映射服务、质量服务、血缘服务 | 管理业务对象、权限、版本、审核流和查询接口。 |
| 任务编排层 | Airflow、Dagster、Temporal、Argo Workflows 等 | 管理批次任务、依赖关系、失败重试、补数和运行日志。 |
| 数据计算层 | SQL 引擎、Spark、Python 规则引擎、术语匹配服务 | 执行数据清洗、转换、映射、校验和质量计算。 |
| 数据存储层 | Raw Zone、Staging Zone、OMOP CDM 库、元数据库、血缘库、对象存储 | 存储原始数据、中间数据、目标数据、元数据和报告文件。 |
| 安全治理层 | RBAC、ABAC、密钥管理、审计日志、脱敏服务、监控告警 | 控制访问、保护敏感数据、记录操作行为和支撑合规要求。 |

### 5.2 前端架构

前端应采用模块化单页应用架构。每个功能域作为独立模块开发，并通过统一的项目、租户、权限和环境上下文串联。

建议前端模块包括：

| 前端模块 | 页面 | 说明 |
|---|---|---|
| 项目管理 | 项目列表、项目详情、环境配置 | 管理医院、研究项目、CDM 版本和数据环境。 |
| 数据源管理 | API 配置、CSV 上传、连接测试、批次列表 | 支持 API、CSV、SFTP、数据库连接等接入方式。 |
| 数据剖析 | 字段画像、缺失率、值域分布、异常样本 | 让用户先看清源数据质量和字段含义。 |
| 清洗规则 | 规则列表、规则编辑器、规则测试、版本对比 | 支持日期解析、单位换算、枚举标准化、去重、派生字段等规则。 |
| OMOP 字段映射 | 源表到目标表、源字段到目标字段 | 支持一源多目标、多源合并和派生字段映射。 |
| OMOP 概念映射 | 术语搜索、候选推荐、人工审核、映射版本 | 管理源编码到标准 concept_id 的映射。 |
| 任务监控 | DAG、运行日志、错误记录、重跑入口 | 展示接入、清洗、映射、转换、验证、发布的状态。 |
| 质量评估 | 总览、表级结果、字段级结果、概念级结果 | 展示质量分、失败项、阻断项和问题样本。 |
| 血缘回溯 | 目标记录反查、源记录影响分析、版本时间线 | 支持从 OMOP 结果查回源数据和处理规则。 |
| 治理中心 | 数据目录、敏感字段、权限审批、发布管理 | 管理数据资产、授权、脱敏和审计。 |

### 5.3 后端架构

后端应拆成业务服务与计算服务两类。业务服务负责对象管理、权限、审核、版本和查询；计算服务负责批处理、规则执行、质量计算和 OMOP 入库。

| 后端服务 | 职责 |
|---|---|
| 认证授权服务 | 管理用户、角色、项目权限、数据权限和操作权限。 |
| 项目服务 | 管理医院、项目、环境、CDM 版本、词表版本和发布版本。 |
| 数据源服务 | 管理 API、CSV、SFTP、数据库连接和接入批次。 |
| 元数据服务 | 管理源表、源字段、字段画像、数据字典和字段标注。 |
| 清洗规则服务 | 管理规则定义、规则版本、规则测试和规则执行结果。 |
| OMOP 映射服务 | 管理字段映射、概念映射、候选推荐、人工审核和映射版本。 |
| 转换执行服务 | 根据映射配置生成 SQL 或 Spark 作业，将 Staging 数据转换到 OMOP 表。 |
| 质量评估服务 | 执行内置质量规则，适配 OHDSI DataQualityDashboard，并解析质量结果。 |
| 血缘服务 | 记录源批次、源行、目标记录、规则版本、映射版本和任务运行之间的关系。 |
| 发布服务 | 冻结规则和映射，将通过验证的数据发布到 OMOP CDM 库。 |
| 审计服务 | 记录查看、导出、修改规则、审核映射、发布、回滚等操作。 |

## 6. 产品功能

### 6.1 数据接入

数据接入模块负责把医院数据安全、稳定地带入平台。来源可以是 API、CSV 文件、SFTP 文件或数据库视图。每次接入必须生成唯一批次号，保存原始文件或原始响应，并记录文件哈希、记录数、字段清单、接入人和接入时间。

核心能力包括：

- API 接入配置：支持 URL、请求方式、Header、认证方式、分页参数、增量字段和拉取频率。
- CSV 上传：支持大文件分片上传、编码识别、分隔符识别、表头识别和失败续传。
- 数据库抽取：支持只读连接、SQL 视图、增量字段和抽取记录数校验。
- 批次管理：展示每次接入的来源、状态、记录数、异常数、文件哈希和处理进度。
- 原始数据保护：原始数据只追加不覆盖，任何清洗和转换都不能直接改写 Raw Zone。

### 6.2 数据剖析

数据剖析用于在映射前理解源数据。平台应对每个源对象自动生成字段画像，帮助用户识别字段含义、数据类型、缺失情况和异常值。

字段画像建议包括：

| 指标 | 说明 |
|---|---|
| 字段类型 | 文本、整数、小数、日期、时间、布尔、枚举等。 |
| 缺失率 | 空值、空字符串、特殊空值编码的比例。 |
| 唯一值数量 | 用于判断字段是否为 ID、枚举或自由文本。 |
| 值域范围 | 数值最小值、最大值，日期最早值、最晚值。 |
| 样本值 | 展示典型样本，辅助人工判断字段含义。 |
| 异常样本 | 展示无法解析、超出范围、格式不一致的数据。 |
| 编码分布 | 对诊断、药品、检验等编码字段展示高频值。 |

### 6.3 数据清洗与归一化

清洗规则应支持可视化配置和高级表达式两种方式。简单规则使用表单配置，复杂规则允许使用 DSL 或 SQL 表达式。

常见清洗规则包括：

- 日期时间解析：处理 `yyyy-MM-dd`、`yyyy/MM/dd`、时间戳、中文日期等格式。
- 空值统一：将 `NULL`、空字符串、`-`、`NA`、`未知` 等统一为空值或指定概念。
- 枚举归一：将 `男/M/1` 统一为男性，将 `女/F/2` 统一为女性。
- 单位换算：如 mg、g、μg、mmol/L 等单位换算。
- 数值清理：去除异常符号，处理 `>10`、`<0.1`、`阴性`、`阳性` 等检验结果表达。
- 去重合并：按患者、时间、事件类型、源记录号识别重复数据。
- 派生字段：从出生日期派生出生年、月、日；从入院出院记录派生就诊时间段。
- 数据过滤：过滤测试患者、无效记录、被撤销医嘱等。

所有规则必须版本化。目标记录需要能追溯到执行它的规则版本。

### 6.4 OMOP 字段映射

字段映射负责把医院源表和源字段转换为 OMOP CDM 的目标表和目标字段。该模块需要支持自动推荐、人工编辑、版本管理和发布冻结。

典型映射关系如下：

| 医院源数据 | 优先映射 OMOP 表 | 关键字段 | 注意事项 |
|---|---|---|---|
| 患者主索引 | PERSON | person_id、gender_concept_id、year_of_birth、month_of_birth、day_of_birth | person_id 生成规则必须稳定，便于跨批次合并。 |
| 门急诊和住院记录 | VISIT_OCCURRENCE | visit_occurrence_id、person_id、visit_concept_id、visit_start_datetime、visit_end_datetime | 需要明确一次就诊的粒度，处理住院转科、多次挂号等情况。 |
| 诊断记录 | CONDITION_OCCURRENCE | condition_concept_id、condition_start_datetime、condition_source_value | 源 ICD 编码应保留在 source_value，并映射到标准 condition concept。 |
| 处方、医嘱、用药 | DRUG_EXPOSURE | drug_concept_id、drug_exposure_start_datetime、quantity、days_supply | 药品名称、规格、剂量和单位需要同时处理。 |
| 手术和操作 | PROCEDURE_OCCURRENCE | procedure_concept_id、procedure_datetime、modifier_concept_id | 手术码、本地操作码和耗材边界要明确。 |
| 检验检查结果 | MEASUREMENT | measurement_concept_id、value_as_number、unit_concept_id、range_low、range_high | 检验项目、检验值和单位换算是高风险区域。 |
| 生命体征、病史、问卷 | OBSERVATION | observation_concept_id、value_as_string、value_as_concept_id | 描述性信息不要强行放入 MEASUREMENT。 |
| 死亡信息 | DEATH | death_date、death_datetime、death_type_concept_id、cause_concept_id | 区分院内死亡、随访死亡和死亡原因来源。 |

字段映射配置建议包含以下信息：

```yaml
target_table: CONDITION_OCCURRENCE
target_field: condition_concept_id
source_object: diagnosis
source_field: diagnosis_code
source_expression: diagnosis_code
transform_rule: map_to_standard_condition_concept
required: true
default_value: 0
mapping_version: MAPPING-2026-001
```

### 6.5 OMOP 概念映射

概念映射是医疗数据转换中最关键的部分之一。平台应把源编码映射到 OMOP 标准概念，并保留源编码与源名称。

自动映射策略建议采用“候选生成 + 置信度排序 + 规则约束 + 人工确认”的方式：

1. 候选生成：根据源编码、源名称、拼音、同义词、历史映射和 OHDSI Vocabulary 表生成候选 concept_id。
2. 置信度排序：根据 exact match、编码体系匹配、文本相似度、domain 一致性、历史确认次数等计算分数。
3. 规则约束：诊断只能映射到 Condition domain，药品只能映射到 Drug domain，检验项目优先映射到 Measurement domain。
4. 人工确认：高置信度可自动通过，但必须保留证据；低置信度进入医学专家复核队列。
5. 版本冻结：映射版本一旦用于发布，不允许直接改写，只能创建新版本。

概念映射页面应展示以下字段：

| 字段 | 说明 |
|---|---|
| source_code | 医院源编码。 |
| source_name | 医院源名称。 |
| source_vocabulary | 源编码体系，如 ICD-10、本地药品码、LIS 项目码。 |
| candidate_concept_id | 推荐的 OMOP concept_id。 |
| candidate_concept_name | 标准概念名称。 |
| domain_id | Condition、Drug、Measurement、Procedure 等。 |
| vocabulary_id | SNOMED、RxNorm、LOINC、ICD10CM 等。 |
| standard_concept | 是否为标准概念。 |
| valid_start_date / valid_end_date | 概念有效期。 |
| confidence_score | 推荐置信度。 |
| review_status | 未处理、自动通过、人工确认、拒绝、需复核。 |

### 6.6 转换执行

转换执行服务根据字段映射、概念映射和清洗规则生成转换作业。中小规模数据可以使用数据库内 SQL 完成，大规模历史数据建议使用 Spark。

转换过程应分为三个区域：

| 区域 | 说明 |
|---|---|
| Raw Zone | 保存原始文件、原始 API 响应或原始表快照。 |
| Staging Zone | 保存完成基础清洗和结构化后的中间表。 |
| OMOP CDM Zone | 保存符合 OMOP CDM 结构的目标表。 |

转换任务应支持全量、增量、按批次重跑、按表重跑和失败节点重跑。任何重跑都不能破坏已经发布的数据版本。

### 6.7 数据验证

数据验证分为入库前验证和发布前验证。

入库前验证关注结构和规则是否正确：

- 目标表是否存在。
- 字段类型是否匹配。
- 必填字段是否为空。
- 主键是否唯一。
- 外键逻辑是否成立。
- 日期字段是否能解析。
- 数值字段是否超出合理范围。
- concept_id 是否存在于词表。
- concept_id 的 domain 是否与目标字段要求一致。

发布前验证关注数据是否适合交付研究使用：

- PERSON、VISIT、诊断、用药、检验等核心表覆盖率。
- 关键字段缺失率。
- 概念映射覆盖率。
- 异常时间顺序，如死亡后还有就诊。
- 检验值和单位是否合理。
- 质量失败项是否达到阻断阈值。

### 6.8 质量评估

质量评估需要同时支持平台内置质量规则和 OHDSI DataQualityDashboard。内置规则用于快速反馈和阻断明显错误，DataQualityDashboard 用于对 OMOP CDM 实例执行系统性质量检查。

质量结果建议分为以下层级：

| 层级 | 示例 |
|---|---|
| 批次级 | 本批次记录数、成功数、失败数、异常数。 |
| 表级 | PERSON 表记录数、VISIT 表覆盖率、MEASUREMENT 表缺失情况。 |
| 字段级 | year_of_birth 缺失率、drug_concept_id 为 0 的比例。 |
| 概念级 | 概念 domain 不匹配、无效 concept_id、非标准概念占比。 |
| 记录级 | 可钻取到失败样本和源记录。 |

质量状态不应只有通过和失败。建议使用以下状态：

| 状态 | 含义 |
|---|---|
| Passed | 已通过。 |
| Warning | 有风险但不阻断发布。 |
| Failed | 未通过，需要修复。 |
| Blocked | 阻断发布。 |
| Waived | 经审批例外放行。 |

## 7. 数据回溯设计

数据回溯是平台的核心能力之一。它需要回答三个问题：

1. 目标 OMOP 记录来自哪条或哪些源记录。
2. 目标字段由哪些源字段、清洗规则和映射规则生成。
3. 某个发布版本使用了哪些源批次、规则版本、映射版本和词表版本。

### 7.1 回溯层级

| 层级 | 回答的问题 | 示例 |
|---|---|---|
| 批次级血缘 | 这一版数据来自哪个批次 | release_id 关联 source_batch_id。 |
| 表级血缘 | OMOP 表由哪些源表生成 | CONDITION_OCCURRENCE 来自 diagnosis 表。 |
| 字段级血缘 | OMOP 字段由哪些源字段生成 | condition_start_datetime 来自 diagnosis_time。 |
| 记录级血缘 | 某条目标记录来自哪条源记录 | condition_occurrence_id 反查 source_row_id。 |
| 规则级血缘 | 目标值经过哪些规则处理 | 日期解析、单位换算、概念映射。 |

### 7.2 建议元数据表

| 表名 | 用途 | 核心字段 |
|---|---|---|
| source_batch | 记录一次 API 拉取或 CSV 上传 | batch_id、source_id、ingest_time、file_hash、record_count、operator。 |
| source_schema | 记录源对象结构 | batch_id、object_name、field_name、data_type、nullable、sample_values。 |
| schema_profile | 记录字段画像 | batch_id、field_name、null_rate、distinct_count、min_value、max_value。 |
| rule_version | 记录清洗规则版本 | rule_version_id、rule_type、expression、test_result、effective_time。 |
| mapping_version | 记录字段映射和概念映射版本 | mapping_version_id、cdm_version、vocabulary_version、status、approved_by。 |
| job_run | 记录任务运行状态 | run_id、batch_id、pipeline_id、start_time、end_time、status。 |
| record_lineage | 连接源记录和目标记录 | run_id、source_object、source_row_id、target_table、target_pk、rule_version_id、mapping_version_id。 |
| quality_check_result | 记录质量检查结果 | release_id、check_name、scope、status、failed_count、threshold、sample_record_ref。 |
| data_release | 记录 OMOP 发布版本 | release_id、cdm_schema、cdm_version、vocabulary_version、quality_score、release_status。 |

## 8. 数据治理设计

数据治理需要覆盖数据目录、权限、敏感字段、审批、审计、版本和生命周期。

### 8.1 数据目录

数据目录按医院、项目、数据源、源对象、OMOP 表和发布版本组织。每个资产需要展示来源、负责人、更新时间、记录数、质量评分、访问说明和关联血缘。

### 8.2 权限模型

权限建议采用 RBAC 与 ABAC 结合的方式。

| 权限类型 | 说明 |
|---|---|
| 功能权限 | 控制用户能否进入数据接入、规则配置、映射审核、质量评估、发布管理等模块。 |
| 项目权限 | 控制用户能访问哪些医院、项目和环境。 |
| 数据权限 | 控制用户能查看哪些表、字段、发布版本和质量报告。 |
| 操作权限 | 控制用户能否上传、编辑、审核、运行、发布、导出、回滚。 |
| 敏感字段权限 | 对姓名、身份证、手机号、住址等字段单独授权。 |

### 8.3 审批与审计

以下操作必须写入审计日志：

- 新增或修改数据源。
- 上传或删除源文件。
- 修改清洗规则。
- 修改字段映射。
- 审核概念映射。
- 运行转换任务。
- 发布或回滚 OMOP 数据版本。
- 查看或导出敏感数据。
- 修改权限和审批配置。

审计日志应包括操作者、操作时间、操作对象、操作前后差异、客户端 IP、审批单号和结果状态。

## 9. 实现方法

### 9.1 前端实现方法

| 能力 | 实现建议 |
|---|---|
| 应用框架 | 使用 React + TypeScript 或 Vue + TypeScript。 |
| 状态管理 | 保存当前租户、医院、项目、环境、CDM 版本和用户权限。 |
| 大表格 | 使用虚拟滚动和服务端分页，避免前端加载全量数据。 |
| 规则编辑器 | 简单规则表单化，复杂规则使用 DSL 编辑器，并提供语法提示和 dry-run。 |
| 映射工作台 | 左侧源字段或源编码，右侧 OMOP 字段或概念候选，中间展示推荐理由和审核状态。 |
| 血缘图 | 使用 DAG 可视化组件，支持节点展开到字段级和记录级。 |
| 质量看板 | 支持按项目、批次、表、字段、检查类型、阻断状态筛选和钻取。 |

### 9.2 后端实现方法

| 能力 | 实现建议 |
|---|---|
| 数据接入 | 连接器框架统一封装 API、CSV、SFTP 和数据库抽取。 |
| 原始数据保存 | 使用对象存储保存文件和响应体，使用元数据库保存批次索引。 |
| 清洗规则执行 | 将规则转换为 SQL、Spark DataFrame 或 Python 函数执行。 |
| 字段映射 | 使用 JSON/YAML 存储 mapping spec，并在数据库中维护版本。 |
| 概念映射 | 导入 OHDSI Vocabulary 表，结合搜索索引和相似度模型生成候选。 |
| OMOP 入库 | 先写 staging schema，通过验证后发布到 cdm schema。 |
| 质量评估 | 内置规则实时执行，发布前调用 DataQualityDashboard。 |
| 任务编排 | 使用 Airflow、Dagster、Temporal 或 Argo Workflows 管理 DAG。 |
| 血缘写入 | 转换作业写入 record_lineage 和字段级 lineage_event。 |

### 9.3 推荐技术选型

| 层级 | 推荐选型 | 说明 |
|---|---|---|
| 前端 | React/Vue + TypeScript | 适合复杂工作台和数据可视化。 |
| 后端 API | Java Spring Boot、Python FastAPI 或 Node.js NestJS | 医疗数据平台更关注权限、审计、任务和稳定性。 |
| 任务编排 | Airflow、Dagster、Temporal、Argo Workflows | 用于批次任务、依赖、失败重试和补数。 |
| 计算引擎 | SQL + Spark | 中小规模用 SQL，大规模历史数据用 Spark。 |
| OMOP 数据库 | PostgreSQL、SQL Server、Oracle | 优先选择团队熟悉且 OHDSI 工具支持较好的数据库。 |
| 对象存储 | MinIO、S3 兼容存储、院内 NAS | 保存 CSV、原始响应、报告和导出文件。 |
| 词表服务 | OHDSI Vocabulary 表 + 本地扩展词典 + 搜索索引 | 支持标准概念查询、候选推荐和本地术语扩展。 |
| 质量工具 | 内置规则 + OHDSI DataQualityDashboard | 内置规则用于实时拦截，DQD 用于发布前系统评估。 |

## 10. 非功能要求

| 要求 | 设计说明 |
|---|---|
| 性能 | CSV 上传支持 GB 级文件分片；字段画像异步执行；千万级记录转换使用数据库内 SQL 或 Spark。 |
| 可靠性 | 任务支持重跑、跳过、恢复和失败节点重试；失败任务不能污染已发布 OMOP schema。 |
| 安全 | 连接凭证进入密钥管理；传输使用 TLS；敏感字段默认加密、脱敏或哈希化。 |
| 合规 | 支持院内部署、最小权限访问、患者标识去标识化、日志留存和数据出域控制。 |
| 可维护性 | 规则、映射、词表、任务 DAG、质量报告和发布版本都要版本化。 |
| 可解释性 | 自动映射必须展示推荐依据，包括命中规则、候选列表、置信度和审核记录。 |
| 可扩展性 | 支持多医院、多项目、多数据源、多 OMOP 版本和多套词表。 |

## 11. MVP 范围

首期不建议覆盖全部 OMOP 表，而应先选择一家医院、一个疾病方向或一个研究项目作为试点，优先打通核心链路。

### 11.1 MVP 1：基础接入与转换

目标是完成从 API 或 CSV 到 OMOP 核心表的首版链路。

范围包括：

- 项目管理。
- 数据源配置。
- CSV 上传或 API 拉取。
- 字段剖析。
- 基础清洗规则。
- PERSON、VISIT_OCCURRENCE、CONDITION_OCCURRENCE、DRUG_EXPOSURE、MEASUREMENT 的字段映射。
- 批次任务运行。
- OMOP staging 入库。

验收信号：试点数据可以稳定写入 OMOP staging，并能查看源批次、规则版本和任务运行记录。

### 11.2 MVP 2：术语映射与质量评估

目标是提升语义映射可信度和入库质量。

范围包括：

- OHDSI Vocabulary 导入。
- 概念候选推荐。
- 人工审核流程。
- 映射版本管理。
- 内置质量规则。
- DataQualityDashboard 适配。
- 质量报告展示。

验收信号：诊断、药品、检验项目形成可复用映射版本，发布前可以生成质量报告。

### 11.3 MVP 3：回溯与治理

目标是满足研究复核、治理和审计要求。

范围包括：

- 记录级血缘。
- 字段级血缘。
- 发布版本管理。
- 权限体系。
- 敏感字段策略。
- 审计日志。
- 发布审批和回滚。

验收信号：从任意目标 OMOP 记录可以反查源记录、清洗规则、映射版本和任务运行。

## 12. 需要补充确认的内容

为了进入研发设计和排期阶段，还需要补充以下信息：

| 待确认内容 | 为什么重要 | 建议产出 |
|---|---|---|
| 试点医院数据清单 | 不同医院 HIS、EMR、LIS、PACS、药房系统差异很大。 | 源系统清单、源表样例、字段字典、API/CSV 样例、数据量估算。 |
| 首期 OMOP 表范围 | OMOP 表很多，首期必须围绕研究目标选择核心表。 | 首期表清单、字段优先级、暂不支持表清单。 |
| 术语体系策略 | 诊断、药品、检验、手术映射难度不同。 | ICD、药品码、LIS 项目、手术码、科室码、单位字典的映射策略。 |
| 数据质量门槛 | 不同研究对质量要求不同。 | 质量规则分级、阻断阈值、例外审批流程。 |
| 患者标识策略 | person_id 生成方式影响跨批次合并、回溯和隐私保护。 | 患者主索引规则、哈希策略、跨系统 ID 合并规则。 |
| 部署与安全要求 | 医院常有内网、等保、数据不出院和数据库类型限制。 | 部署拓扑、安全基线、访问控制模型、备份恢复要求。 |
| 团队分工 | OMOP 项目需要产品、数据工程、医学术语、前后端、测试和运维共同参与。 | RACI 分工表、审核流程、上线流程。 |
| 验收标准 | 没有量化标准会导致“能入库但不可用”。 | 接入成功率、映射覆盖率、质量通过率、回溯可查率、任务时效。 |

## 13. 建议接口

| 接口 | 方法 | 用途 | 返回重点 |
|---|---|---|---|
| `/api/projects/{id}/sources` | POST | 创建数据源 | source_id、连接状态、字段探测任务号。 |
| `/api/batches/{id}/profile` | GET | 查看批次画像 | 字段统计、异常样本、推断类型。 |
| `/api/rules/{id}/dry-run` | POST | 测试清洗规则 | 输入样本、输出样本、错误原因、影响记录数。 |
| `/api/mappings/field/recommend` | POST | 字段映射推荐 | 候选 OMOP 表字段、置信度、推荐理由。 |
| `/api/mappings/concept/recommend` | POST | 概念映射推荐 | 候选 concept_id、domain、vocabulary、标准概念状态。 |
| `/api/pipelines/{id}/runs` | POST | 运行转换任务 | run_id、DAG 节点状态、日志入口。 |
| `/api/releases/{id}/quality` | GET | 查看质量结果 | 质量评分、失败检查、阻断项、报告链接。 |
| `/api/lineage/trace` | GET | 查询血缘 | 源记录、目标记录、规则版本、映射版本、任务运行。 |

## 14. 关键风险

| 风险 | 表现 | 缓解方式 |
|---|---|---|
| 源数据质量不可控 | 字段缺失、日期混乱、编码不规范、重复数据多。 | 先做字段画像和质量基线，不直接进入 OMOP 转换。 |
| 概念映射错误 | 本地诊断、药品、检验映射到错误 domain 或错误 concept。 | 自动推荐只能给候选，高风险映射必须人工审核。 |
| 回溯粒度不足 | 只能查批次，不能查到源记录和规则。 | 从第一版就设计 record_lineage 和 rule_version。 |
| 首期范围过大 | 同时覆盖过多 OMOP 表，导致延期。 | 首期聚焦 PERSON、VISIT、诊断、用药、检验。 |
| 质量报告不可解释 | 只有分数，没有失败样本和处理建议。 | 质量结果必须能钻取到表、字段、规则和源记录。 |
| 数据安全不满足院内要求 | 敏感数据出域、权限过粗、审计不足。 | 支持院内部署、字段级权限、脱敏和审计日志。 |
