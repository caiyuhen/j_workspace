🌊 Wave 10 · End-to-End PubMed + Dashboard 三种架构方案

基于 W1-W9 现有底座（检索→去重→9a筛选→9c分流→9b质量→W5 GRADE→W8.4 报告输出）。目标：真实 PubMed 50-200 篇一键跑通 5 阶段 + 可视化 Dashboard。

✅ 推荐 · 方案 C

编排 Pipeline Orchestrator（Celery-free，asyncio Task 状态机 + DB）

新增 1 个 PipelineRun 数据表 + pipeline_engine.py 编排协程。前端轮询 /pipelines/{id}。不引入 Redis/Celery，用 Python asyncio + SQLite，单机一次管 8 个并发 run。

Pros / Cons

  • ✅ 0 新依赖（不引入 Redis/RQ）
  • ✅ 错误隔离：单步失败 → 标记 failed_step，UI 给出重试按钮
  • ✅ 可 resume：同一 run 从断点继续（不是从头跑）
  • ✅ 历史 run 可回放（DB 保留）→ 做 A/B 对比
  • ⚠️ 单机并发 ≤ 8（够科研用，不够再换 Celery）
  • ⚠️ 进程被杀时，run 状态保留，下次启动自动 resume queued

方案 B · 同步串行 + Long-Poll SSE

Synchronous Chained Router（SSE 流式推进度）

单个 POST /pipelines/run-sync 同步调 8 步，用 SSE (text/event-stream) 每步推 event。连接断=用户看不到中间态，但后端完整跑完。

核心数据流

[前端 EventSource('/pipelines/run-sse')]
  → onmessage({step:"W8_search",n:86,total:100})
  → onmessage({step:"9a_screening_ta",...})
  → onmessage({step:"done",report_url:"/..."})
  • ✅ 实现简单（无 DB 表，无状态机）
  • ⚠️ 浏览器 tab 切后台，SSE 可能被掐
  • ⚠️ 进程 kill → 结果全丢（无法 resume）
  • ⚠️ 只支持 1 用户 1 run（GIL 单线程）

方案 A · 重型

Celery + Redis + Flower（生产级）

补 Redis 容器 + Celery Worker + Flower 监控面板。学术项目 2026 年内一般用不到这么重。可升级路径：方案 C → 切 Celery Broker。

🟢 推荐最终选：方案 C（Pipeline Orchestrator asyncio + DB）。理由 3 条：
① 3 天可交付，能赶在用户切回手动 pubmed 搜索前上线；
② 零新依赖 + 完全 append-only NOTOUCH；
③ concurrency 顶到 8 个并发 run = 足够 8 个 researcher 同时工作，后续换 Celery 只动 1 个文件（broker 抽象）。

❓ 下一个问题（请回答）
