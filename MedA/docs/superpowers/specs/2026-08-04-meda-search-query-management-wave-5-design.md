# MedA Wave 5 检索式管理页设计文档

> 设计日期：2026-08-04
> 设计范围：检索阶段子入口深页 `检索式管理`
> 适用阶段：Wave 5 设计确认

## 1. 设计目标

本设计文档用于定义 MedA 在 `Wave 5` 阶段优先落地的第一个真实子入口工作页：`检索式管理`。

在 `Wave 4` 中，系统已经完成：

- 首页 -> 阶段入口页 的统一承接
- 六阶段共用 `通用阶段壳`
- 阶段入口页内的子入口导航、最近任务、最近产物、阶段助手

`Wave 5` 的目标不再是“告诉用户下一步去哪”，而是让用户进入一个真正可工作的深页。第一波选择 `检索链路`，并优先把 `检索式管理` 做成真实可用页。

本波要先打实的核心能力是：

- 组织检索词组
- 组合结构化检索式
- 保存版本
- 提供执行前校验与短反馈

## 2. 已确认设计决策

- `Wave 5` 优先对象为 `检索链路`
- 第一深页选择 `检索式管理`
- 页面骨架采用 `A. 三段式编辑器`
- 中间主编辑区采用 `块式编辑`
- 左侧词组区按 `PICO / 主题分组` 组织
- 第一波不追求完整数据库执行引擎与结果全页

## 3. 核心定位

`检索式管理` 是检索阶段入口页往下的第一层真实工作页。它的定位已经从“入口枢纽页”切换为“主工作页”。

它优先回答三个问题：

- 当前检索式是怎么组织的
- 当前检索式是如何组合出来的
- 下一步应该保存、调整还是执行

它不是版本中心，不是结果中心，也不是数据库来源配置中心，而是检索阶段中最核心的检索式构建与维护页面。

## 4. 整体方案

### 4.1 目标工作流

`Wave 5` 第一波希望先打通这条最小真实工作流：

`组织词组 -> 加入编辑区 -> 组合检索式 -> 执行前校验 -> 保存版本`

只要这条主链路真实可走通，系统就完成了从“阶段入口页”到“深业务页”的第一次跃迁。

### 4.2 方案选型

针对 `检索式管理` 第一屏的骨架，本轮评估过三种方向：

- `A. 三段式编辑器`
- `B. 双栏主编排`
- `C. 上下式流程页`

最终选择 `A. 三段式编辑器`，原因如下：

- 更适合把“词组组织 / 检索式编辑 / 预览反馈”三类信息同时放在首屏
- 既符合科研检索的组织方式，也保留专业工作台的持续编辑感
- 最利于后续做结构化追溯、版本和执行链路

## 5. 页面结构

本页继续挂在现有工作台壳层内，不脱离项目上下文，不切出独立产品式页面。

整页保持外层四段结构：

1. `左侧窄导航`
2. `左侧项目上下文面板`
3. `中间主工作区`
4. `右侧辅助区`

### 5.1 左侧窄导航

左侧窄导航与前面各波保持一致：

- 工作台
- 项目
- 数据 / 资料
- Agent
- 产物
- 管理

这里不新增检索式管理专属层级，避免全局导航复杂化。

### 5.2 左侧项目上下文面板

左侧项目上下文面板继续负责说明当前项目上下文，建议保留：

- 当前项目名称
- 项目标识
- 所属机构
- 当前阶段：检索
- 返回检索阶段入口页的快捷入口

这一区域依旧回答“我现在在哪个项目里”，不承担检索式深编辑内容。

### 5.3 页面轻量头部

在中间主工作区上方保留一个轻量头部，至少包含：

- 页面标题：`检索式管理`
- 当前项目名称
- 当前阶段：检索
- 当前检索式名称
- 返回上一级阶段页入口

这层的目标是让用户即使进入深页，也始终知道当前页面属于哪个项目、哪个阶段、哪条检索式。

### 5.4 深页打开模式与规范路由

为避免 `Wave 5` 在实现时退化成“只有一个匿名编辑器”，本页需要明确深页的规范打开模式。

`Wave 5` 采用以下最小路由语义：

- `workspace / project / search / query-builder`
  - 打开当前项目下最近一次检索式草稿
  - 如果项目下尚无检索式，则创建一条默认草稿并进入

- `workspace / project / search / query-builder ? query_id = xxx`
  - 打开指定 `query_id` 的当前草稿
  - 如果该 `query_id` 没有草稿，则回退到该检索式最近一次版本快照并提示“需派生草稿后编辑”

- `workspace / project / search / query-builder ? query_id = xxx & version = vN`
  - 打开指定版本快照
  - 版本快照默认只读
  - 用户可通过“派生为草稿”进入新的可编辑草稿态

这里的路由写法在不同端可映射为实际 URL、内部路由状态或宿主导航参数，但语义必须一致：

- 始终带着同一个 `ResearchProject`
- 可以明确区分“打开草稿”与“打开版本快照”
- 可以从深页稳定返回 `检索阶段入口页`

## 6. 三段式编辑器结构

### 6.1 左段：词组与字段区

左段按 `PICO / 主题分组` 组织检索词组。第一波建议固定为以下分组：

- 人群 / 疾病
- 干预 / 暴露
- 对照 / 比较
- 结局
- 补充限定

每个分组至少展示：

- 分组名称
- 已加入的检索词块
- 词来源标记，例如 `主题词` / `自由词`
- 简单新增入口

左段职责是 `组织原材料`，不是直接写出最终检索式。

### 6.2 中段：块式编辑器

中段是整页核心，用于把左侧词组转成结构化检索式。

第一波块类型只保留最小集合：

- 词组块
- `AND`
- `OR`
- `NOT`
- 括号分组块

中段内部建议分三层：

1. `顶部版本条`
   - 当前版本
   - 保存
   - 另存为新版本
   - 执行

2. `主编辑画布`
   - 检索式块组合区
   - 按顺序显示当前组合结构
   - 支持基础重排与分组

3. `底部辅助提示`
   - 语法校验
   - 组合建议
   - 当前检索式摘要

中段职责是 `形成结构化检索式`，并让检索式本身可追溯、可保存、可继续修改。

### 6.3 右段：预览 + 助手

右段只放短反馈，不放重结果页。

第一波建议包含：

- 命中量预览
- 覆盖数据库摘要
- 当前问题提醒
- 助手建议动作

例如：

- 某个主题组缺失
- `NOT` 过强可能误排
- 建议补充主题词
- 建议保存新版本后再执行

右段职责是 `辅助决策`，不是替代执行结果页面。

## 7. 关键交互规则

### 7.1 左段进入中段

左侧词组区不是只读展示，必须能进入中段编辑器。

第一波不做高自由拖拽，先采用更稳的交互：

- 点击词块 `加入编辑区`
- 在中段形成一个结构化块
- 再通过简单操作完成组合

建议第一波只支持这些基础操作：

- 上移
- 下移
- 切换 `AND / OR / NOT`
- 包裹分组
- 删除块

这样更容易双端统一，也更适合 TDD 推进。

### 7.2 保存与版本

本页要先具备真实保存能力。第一波至少支持：

- 保存当前版本
- 另存为新版本
- 标记是否有未保存改动

这里的保存不是纯前端状态切换，而应在后续实现中落到真实数据承接结构上。

`Wave 5` 明确采用 `可变草稿 + 不可变版本快照` 模型：

- 用户进入编辑页时，默认编辑的是一条 `query draft`
- `保存`
  - 保存当前草稿内容
  - 不创建新版本号
  - `query_dirty` 变为 `false`

- `另存为新版本`
  - 以当前草稿内容生成一个新的不可变版本快照
  - 新版本号递增，例如 `v1 -> v2`
  - 当前草稿继续保留，并与最新版本内容同步

- `版本快照`
  - 默认只读
  - 不能在原版本上直接覆盖修改
  - 如需继续编辑，应先“派生为草稿”

这样可以在 `Wave 5` 先把“编辑态”和“可追溯版本”稳定分开，避免把版本系统做成不可控的复杂状态机。

### 7.3 执行前校验

第一波即使不完整接数据库执行，也必须具备执行前校验反馈。

至少包含：

- 是否为空
- 是否只有单边词组
- 是否括号不平衡
- 是否缺少关键主题组

也就是说，本波先把“能不能执行”的判断做起来。

### 7.4 右侧短反馈

右侧只给短反馈，不下沉为大结果页。优先展示：

- 当前检索式摘要
- 预计覆盖范围
- 问题提醒
- 助手建议

这里的 `预计覆盖范围 / 命中量预览 / 覆盖数据库摘要` 在 `Wave 5` 不代表真实检索执行结果，而采用 `heuristic preview` 语义：

- 来源于本地规则计算、已选数据库来源快照、当前块结构摘要
- 不触发真实数据库检索
- 不要求连接完整执行引擎
- 可返回 `available / unavailable / stale` 三种状态

其中：

- `available`
  - 当前草稿具备基础结构，系统可以给出启发式摘要
- `unavailable`
  - 当前草稿为空、结构不完整或缺少最小数据库来源信息
- `stale`
  - 当前 preview 基于最近一次保存或最近一次版本快照生成，和当前未保存草稿不完全一致

因此，`Wave 5` 的右侧 preview 本质上是“执行前短反馈”，不是“真实命中结果页”。

### 7.5 返回链路

用户必须能够清楚地：

- 从 `检索式管理` 返回 `检索阶段入口页`
- 从 `检索阶段入口页` 返回 `工作台首页`
- 全程保持同一 `ResearchProject` 上下文

## 8. 数据与状态语义

虽然 `Wave 5` 第一波不深做完整执行引擎，但页面至少要围绕以下语义工作：

- `query_id`
- `query_name`
- `query_version`
- `query_dirty`
- `query_mode`
- `grouped_terms[]`
- `expression_blocks[]`
- `validation_messages[]`
- `preview_summary`

其中：

- `grouped_terms[]` 对应左段 `PICO / 主题分组`
- `expression_blocks[]` 对应中段块式编辑器
- `validation_messages[]` 对应底部校验和右段问题提醒
- `preview_summary` 对应右段预览信息

为保证实现可拆解，`Wave 5` 再补充以下最小契约：

- `query_id`
  - 检索式主实体标识
  - 一个项目下可存在多条检索式

- `query_name`
  - 当前检索式名称
  - 用于头部展示、版本标识和后续列表承接

- `query_version`
  - 当前打开的版本号
  - 当页面处于草稿态时，它表示“草稿基于哪个最近版本派生”

- `query_mode`
  - 取值限定为 `draft` 或 `snapshot`
  - `draft` 代表可编辑
  - `snapshot` 代表只读版本快照

- `grouped_terms[]`
  - 每项至少包含：
    - `group_key`
    - `group_label`
    - `terms[]`
  - `terms[]` 每项至少包含：
    - `term_id`
    - `label`
    - `source_type` (`controlled` / `free_text`)
    - `selected`

- `expression_blocks[]`
  - 每项至少包含：
    - `block_id`
    - `block_type` (`term` / `operator` / `group`)
    - `operator` (`AND` / `OR` / `NOT`, 可为空)
    - `term_ref`
    - `children[]`
    - `position`

- `validation_messages[]`
  - 每项至少包含：
    - `level` (`error` / `warning` / `info`)
    - `code`
    - `message`

- `preview_summary`
  - 每次只表达短反馈
  - 至少包含：
    - `status` (`available` / `unavailable` / `stale`)
    - `coverage_hint`
    - `database_scope_summary`
    - `estimated_hit_band`
    - `last_generated_from`

`last_generated_from` 用于明确 preview 是基于：

- 当前草稿即时结构
- 最近一次保存的草稿
- 最近一次版本快照

这样后端、shared-sdk、Web、Desktop 后续都能围绕一套清晰语义扩展，而不是把状态散落在多个局部组件里。

### 8.1 本波最小实体关系

`Wave 5` 只要求引入最小实体关系，不引入完整检索执行子系统：

- `SearchQuery`
  - 代表一条检索式
  - 挂在同一个 `ResearchProject` 下面

- `SearchQueryDraft`
  - 代表当前可编辑草稿
  - 一条 `SearchQuery` 同一时刻最多只有一条当前草稿

- `SearchQueryVersion`
  - 代表不可变版本快照
  - 由“另存为新版本”生成

最小关系为：

`ResearchProject -> SearchQuery -> { SearchQueryDraft, SearchQueryVersion[] }`

第一波只需要支撑：

- 读取当前草稿
- 保存当前草稿
- 从当前草稿创建新版本
- 读取指定版本快照
- 从指定版本派生草稿

## 9. Wave 5 实现边界

本波明确只把 `检索式管理` 这一个子入口页做成真实深页，不同时深做：

- 数据库来源真实配置页
- 检索记录时间线页
- 完整数据库执行结果全页
- 高自由拖拽编排器
- 多人协作冲突处理

`Wave 5` 的重点是：

- 真实页面结构
- 真实词组组织
- 真实块式组合
- 真实保存入口
- 真实执行前校验
- Web / Desktop 同构

本波默认包含以下真实能力：

- `query draft` 的创建与读取
- `query draft` 的保存
- 从 `draft` 生成 `version snapshot`
- 指定 `query_id / version` 的只读打开
- 从 `snapshot` 派生回 `draft`
- 基于规则的 `heuristic preview`

本波明确不包含：

- 实时数据库命中查询
- 跨数据库真实执行聚合
- 版本差异比对中心
- 检索式多人并发编辑
- 检索式库总览页

## 10. 验收标准

`Wave 5` 完成后，至少应满足：

- 用户可从检索阶段入口页进入真实的 `检索式管理` 工作页
- 页面采用 `A 三段式编辑器`
- 左段按 `PICO / 主题分组` 展示词组
- 中段可形成基础块式检索式组合
- 页面支持保存 / 另存为新版本 / 未保存状态提示
- 页面提供执行前校验反馈
- 右段提供预览与助手短反馈
- Web 与 Desktop 保持同构信息架构
- 返回阶段入口页和工作台首页的链路清楚可达
- 页面可区分 `draft` 与 `snapshot` 两种打开模式
- 指定 `query_id / version` 可被稳定重开
- preview 明确为 `heuristic preview`，不要求真实执行结果

## 11. 风险与控制点

- 如果第一波就做高自由拖拽，范围和实现复杂度会迅速失控
- 如果第一波就接完整数据库执行结果页，会把重点从“检索式管理”转移到“结果中心”
- 如果把数据库来源、检索记录、执行结果一起深做，会把单页扩成整个子系统
- 如果左段直接按数据库字段组织，会削弱科研检索的主题语义

控制策略：

- 先用点击加入和基础重排替代复杂拖拽
- 右段只做短反馈，不做大结果页
- 只深做 `检索式管理`，其余检索子入口继续保留承接层
- 左段坚持 `PICO / 主题分组`

## 12. 设计结论

MedA `Wave 5` 应优先实现 `检索链路` 下的 `检索式管理` 深页，并采用 `A 三段式编辑器`。左段按 `PICO / 主题分组` 组织词组，中段采用 `块式编辑器` 形成结构化检索式，右段提供 `预览 + 助手` 的短反馈。本波不追求完整检索执行子系统，而是先把“组织词组 -> 组合检索式 -> 保存版本 -> 执行前校验”这条真实主工作流做实，为后续数据库来源、检索记录和执行结果页扩展提供稳定上层结构。
